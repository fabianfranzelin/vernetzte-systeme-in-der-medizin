Requirements

What a networked medical device must offer

  1. Interoperability — multi-vendor plug-and-play in the OR / at home
  2. Real time — alarms, closed-loop control, streaming vitals
  3. Safety — IEC 62304, ISO 14971, IEC 60601-1
  4. Security — IEC 62443, MDR, threat modelling
  5. Traceability — who did what, when, from which device
  6. Scalability — device → room → hospital → network

A single scenario forces all six

  • Wearable sends TidalVolume, HeartRate, StepCadence.
  • Dashboard subscribes, renders, raises an alert if a threshold is crossed.
  • Multiple vendors. Multiple networks. Multiple regulatory jurisdictions.

These are the non-functional requirements. They drive the architecture.

Deep dive — SDC / IEEE 11073

IEEE 11073 — a family, not a single standard

Part Scope
11073-10207 Domain Information & Service Model (BICEPS)
11073-20701 Service-Oriented Device Connectivity (SDC)
11073-20702 Medical DPWS binding (transport)
11073-10101(nu) Nomenclature codes for vitals, alarms, events

BICEPS = Basic Integrated Clinical Environment Protocol Specification.

The three roles in SDC

  • Provider — a medical device that offers services (a ventilator).
  • Consumer — a system that consumes them (a monitor, a dashboard).
  • SDC network — discoverable, self-describing, secured.

Everything above the network layer is domain-specific medical semantics.

BICEPS descriptors — static structure

Every provider hosts an MDIB (Medical Device Information Base): 

MDIB Descriptors
├── MDS      Medical Device System
├── VMD      Virtual Medical Device
├── Channel
└── Metric   ← e.g. StepCadence

Descriptors say what exists; they do not change during a session.

BICEPS states — live values

The state tree carries the current values against each descriptor: 

MDIB States
├── NumericMetricState             single scalar
├── StringMetricState               textual value
├── RealTimeSampleArrayState        waveform, sampled data
├── AlertConditionState             is a condition present?
└── AlertSignalState                is the alarm currently on?

The four service groups

  • Get Service — pull the MDIB, one snapshot.
  • Set Service — change device settings (with safety context!).
  • Description / State Event Service — push updates to subscribers.
  • Context Service — who is the patient, which location, which workflow?

Safety Contexts — the hard part

A Set operation is not just an RPC. The consumer must include a Safety Context proving:

  • the right patient is targeted (PatientContext),
  • the right location (LocationContext),
  • the right workflow (WorkflowContext),
  • and that the operation is permitted right now (Participant Keys).

This is where SDC earns the word "medical".

Transport — Medical DPWS

  • WS-Discovery over UDP multicast — how devices find each other
  • SOAP/HTTP(S) over TCP — for messages
  • WS-Eventing — for subscriptions
  • TLS — transport security
  • WS-Security + XML Signature — message integrity above TLS

Side-by-side

Concern Automotive Medical

What transfers, what does not

Transfers well:

  • Service-oriented architectural patterns
  • QoS-based real-time streaming
  • Risk-based V-model and traceability discipline
  • Test infrastructure and simulation (my digital-twin work at Bosch)

Does not transfer:

  • Domain semantics — BICEPS is medicine, VLANs are cars
  • Clinical benefit in the risk equation — unique to medicine
  • Patient / workflow context — no analogue in the vehicle

The insight

Architectural patterns are transferable. Domain semantics are not.

That is where the real engineering happens. And that is what I want to teach and research at Reutlingen.

SDC vs. FHIR — one line

  • SDC: real-time, device-to-device, inside a clinical space, milliseconds.
  • FHIR: system-to-system, cross-institution, over the internet, seconds.

They are complementary, not competing.
